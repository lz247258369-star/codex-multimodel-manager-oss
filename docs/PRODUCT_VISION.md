## 1. 一句话定位

一个 Windows 上的 Codex 多模型管理器：**优先使用 ChatGPT 订阅账户的官方模型；只有当前模型的额度明确耗尽时，才自动切换到可用的备用模型；未耗尽时保持当前模型；用户随时可以手动切换，手动切换后自动额度切换继续有效。** 它同时管理 Provider、模型目录、Codex CLI / Desktop 集成、本地 Router、安装升级回滚与安全边界。

## 2A. 产品原则（不可协商）

1. **官方优先**：ChatGPT 订阅账户的官方模型是默认首选；第三方模型是补充，不是替代。
2. **不耗尽不切换**：只有明确的额度/余额耗尽才触发跨模型切换（G-2、G-3）。
3. **人工优先，且不强制切回**：用户的手动选择永远优先于自动切换；手动选择后，自动额度切换在下一次耗尽时重新生效（G-4）；原模型额度恢复后不自动强制切回（G-5）。
4. **有界失败**：全部备用模型都不可用时停止尝试、明确报告失败原因，不无限重试，不擅自扩大到未批准的 Provider（G-6）。
5. **不静默**：发现新模型、身份推断、模型迁移、付费探测、配置写入都需要显式确认（AGENTS.md 第 9–11 条）。
6. **密钥不出边界**：只保存环境变量引用；不读取 `auth.json`；不代理 ChatGPT 账户凭据。
7. **可回滚**：任何对 Codex 配置的修改都有备份与精确恢复路径；Direct Mode 始终可用并且是默认。
8. **项目代码与模型切换隔离**：切换模型绝不执行 `git reset` / `git clean` / `git stash`。
9. **证据优先**：没有证据就报告 UNKNOWN，而不是猜测成功。

## 5. 最终架构（目标形态）

```text
┌────────────────────────── 用户 ──────────────────────────┐
│  V4 Visual Console（WPF）        Codex CLI / Codex Desktop │
└──────┬──────────────────────────────┬──────────────────────┘
       │ 显式动作（备份/回滚）           │ 普通对话请求
       ▼                              ▼
┌──────────────────┐        ┌─────────────────────────────────┐
│ Manager 运行时     │        │ Direct Mode                       │
│ (PowerShell/Skill)│──────▶│  ChatGPT 订阅账户（DIRECT_ONLY）    │
│ 配置·发现·批准·    │        │  第三方 Provider（Responses）       │
│ 健康·handoff       │        └─────────────────────────────────┘
│ 安装·升级·卸载      │        ┌─────────────────────────────────┐
│ 生命周期控制器      │──────▶│ Local Router（opt-in，127.0.0.1） │
└──────────────────┘        │  Ingress → 线程级选择(HS-1B)       │
                            │  → 额度耗尽粘性切换(HS-1C)          │
                            │  → 解析/能力/健康 → Provider 适配器 │
                            │  控制面（认证、脱敏）→ V4             │
                            └─────────────────────────────────┘
```

关键边界：

- **ChatGPT 订阅账户的流量不经过 Router**（架构中为 `DIRECT_ONLY`：Router 不读取 `auth.json`、不代理 ChatGPT 账户凭据）。因此在现有 Router 架构内看不到 ChatGPT 订阅额度耗尽事件。ChatGPT 订阅额度的检测与自动切换是**已明确的产品目标；当前尚无经过验证的可行实现；需要独立技术可行性研究**（见 §6.1）。这既不表示无法实现，也不表示已经可以实现。
- Router 默认关闭；任何启用都是用户显式 opt-in，并保留 Direct Mode 精确恢复。
- Desktop 原生模型选择器不显示自定义模型（平台限制），同线程切换依赖 Router 侧线程级覆盖。

## 6. 尚未解决的问题（技术研究与老板决策）

1. **ChatGPT 订阅额度的检测与自动切换（G-2…G-5 对 ChatGPT 订阅额度的适用）。**
   状态：**已明确的产品目标；当前尚无经过验证的可行实现；需要独立技术可行性研究。**
   现有 HS-1C 设计只覆盖 Router 内第三方 Provider 之间的切换。对 ChatGPT 订阅额度，需要研究：如何在不读取、不代理账户凭据的前提下，可靠识别“ChatGPT 订阅额度已耗尽”，以及如何把后续请求切换到备用模型。研究方向（均**未验证**，只是研究输入，不是结论）：
   - (a) Codex 自身是否暴露可用的额度/限流信号（例如 app-server 事件或错误码），可被 Manager / Router 只读获取；
   - (b) 在 Codex 客户端侧（CLI / Desktop）由 Manager 观察到耗尽后改道到 Router 备用路由的可行路径；
   - (c) 其他不违反 AGENTS.md 安全原则的路径。
   **OpenAI API 路由（`mm_openai_api`）是独立的额度来源，不能替代 ChatGPT 订阅额度的目标。**
   “提示 + 一键切换”只能在可行性研究结束后、经老板批准作为**降级方案**；在老板批准前，它不得替代“自动切换”这一已确认的目标。
   研究本身不新增任何产品能力：在研究证据被老板接受之前，不得把“自动查询额度/余额”或任何未经验证的额度检测机制写入产品或路线图作为已有能力。该研究在 MASTER_ROADMAP 的 M1 进行，先于 V1 范围冻结（M2）。
2. Router 是否进入 V1，或 V1 以 Direct Mode + V4 为主、Router 作为 opt-in Beta。
3. Desktop 同线程自动切换是否是 V1 必需项（受实机验收不足约束）。
4. 是否采用 OpenCodex（Draft #67）这类第三方依赖。

## 7. 非目标（除非老板另行批准）

- 远程 / 多用户 Router 服务；
- 修补或注入官方 Codex Desktop / CLI；
- 读取或代理 ChatGPT 账户凭据；
- 基于价格或延迟的自动跨模型切换；
- 主动查询额度/余额（未经验证、未经批准；HS-1C 设计只依据请求实际返回的明确耗尽信号判断，ChatGPT 订阅额度的检测方式待 §6.1 研究）；
- 全部备用模型不可用时的无限重试，或未经确认扩大到未批准的 Provider（G-6）；
- 计费对账或计费保证（成本只做估算）；
- 未经确认的付费推理。
